spec

moonbitstack/mooncrypt/spec

Constant-time comparison, NIST SP 800-57 Part 1 §8 (key destruction): https://doi.org/10.6028/NIST.SP.800-57pt1r5

The contracts every other package in mooncrypt is written against, plus the two operations that must not be written casually: comparing secrets and erasing them.

traitAead
pub(open) trait Aead { fn seal(Self, nonce~ : BytesView, plain~ : BytesView, aad~ : BytesView) -> Bytes fn open(Self, nonce~ : BytesView, cipher~ : BytesView, aad~ : BytesView) -> Bytes raise Broken }

Authenticated encryption with associated data.

[`open`] raises rather than returning an option, because "the tag did not match" is the one outcome a caller must not silently treat as empty plaintext. `cipher~` is the ciphertext with its tag appended, the layout every AEAD construction in use writes.

traitBlock
pub(open) trait Block { fn block(Self) -> Int32 fn encrypt(Self, BytesView) -> Bytes fn decrypt(Self, BytesView) -> Bytes }

A block cipher: a keyed permutation of a fixed-size block.

It is the thing a mode of operation is built on, which is why it is a contract rather than a concrete type — GCM is defined for any 128-bit block cipher, so it takes one of these and SM4-GCM costs nothing more than an SM4 that implements it.

Both directions are here although a counter mode needs only [`encrypt`]: a permutation that cannot be inverted is not a block cipher, and a mode such as CBC needs the inverse.

traitHash
pub(open) trait Hash { fn write(Self, BytesView) -> Unit fn finish(Self) -> Bytes fn reset(Self) -> Unit fn size(Self) -> Int32 fn block(Self) -> Int32 }

A cryptographic hash, as a state you feed and then read.

Five methods and no more, because everything mooncrypt builds on top of a hash needs exactly these: HMAC needs [`block`] to size its pads, HKDF and PBKDF2 need [`size`] to count output blocks, and every one-shot needs [`write`] then [`finish`]. A third-party digest becomes usable throughout the library the moment it implements this.

[`finish`] does not consume the state, so a caller may keep writing and read again; [`reset`] returns it to the initial vector, which is how HMAC reuses one allocation for both passes.

traitMac
pub(open) trait Mac { fn write(Self, BytesView) -> Unit fn finish(Self) -> Bytes fn size(Self) -> Int32 }

A message authentication code: a hash that a key has been mixed into.

It is deliberately not a [`Hash`] — a MAC has no block size worth exposing and must never be used where an unkeyed digest is expected.

fneq
pub fn eq(BytesView, BytesView) -> Bool

Compare two byte strings in time that does not depend on their contents.

The obvious loop returns at the first differing byte, and the time it took tells an attacker how long a prefix they guessed right — enough to recover a tag or a token byte by byte across many requests. This one reads both strings to the end and folds the differences together.

Length is not treated as a secret: unequal lengths answer immediately, which is what every library does, because the length is visible on the wire anyway.

This is the only comparison mooncrypt offers. Use it for tags, digests and anything else derived from a key.

fnwipe
pub fn wipe(FixedArray[Byte]) -> Unit

Overwrite a buffer with zeroes.

Key material lives longer than the code that used it: a scratch array stays in whatever memory the runtime hands out next until something else writes over it. Erasing at the end of the operation shortens that window. Under a garbage collector it is a best-effort measure, not a guarantee — a copy the collector moved is out of reach — which is why keys are held in [`FixedArray`] here rather than in [`Bytes`], where they could not be erased at all.

ripemd

moonbitstack/mooncrypt/hash/ripemd

RIPEMD-160, from the European RIPE project (Dobbertin, Bosselaers, Preneel, 1996).

Two parallel lines of eighty rounds, mixed at the end rather than during: the design is MD4's compression function run twice with different constants and message orders, and the result combined across both lines. That is what makes it a different hash rather than a stronger MD4, and it is why the two lines cannot be computed separately.

It is legacy. No new protocol should pick it — SHA-2 and SHA-3 are faster on every target that matters and have had far more attention — but Bitcoin's address format, OpenPGP fingerprints and a long tail of older systems all still name it, and a library that cannot compute it cannot interoperate.

cmac

moonbitstack/mooncrypt/mac/cmac

CMAC, NIST SP 800-38B: https://doi.org/10.6028/NIST.SP.800-38B

CBC-MAC was already known to be broken for messages of different lengths: the tag of one message is the tag of a longer one that continues it. CMAC fixes that by deriving two subkeys from the cipher and mixing a different one into the last block depending on whether the message ended on a block boundary. The result is a MAC that works for any length and over any block cipher.

What GCM reduces to when there is no plaintext: GHASH over the associated data and the length block, encrypted with the counter. 01

argon2

moonbitstack/mooncrypt/kdf/argon2

Argon2, RFC 9106: https://www.rfc-editor.org/rfc/rfc9106

The memory-hard function that won the Password Hashing Competition. Where scrypt ties its guarantee to one pass over a buffer, Argon2 builds a thousand-block matrix and reads it back at pseudo-random positions, so the cost of a guess is set by how much memory an attacker is willing to buy.

All three variants are here because they share everything except where the addresses come from: Argon2d reads them from the data, which is fastest but leaks through cache timing; Argon2i derives them from a counter, which is side-channel free but needs more passes; Argon2id does the first half-pass data-independently and the rest not, which is why RFC 9106 recommends it.

typeParams

The three numbers a derivation is defined by.

`memory` is in kibibytes, and it is what the function is really about: the derivation allocates that much and reads it back in a password-dependent order, so an attacker who cannot afford the memory cannot compute the hash cheaply at all. `passes` multiplies the time without changing the memory. `lanes` is how many independent chains are kept; it is the only knob that helps when the work runs on a GPU, and each lane needs eight blocks.

The tag length is not here: it is an argument to the derivation, because two calls that differ only in how long an output they want are still the same function with the same cost.

bcrypt

moonbitstack/mooncrypt/kdf/bcrypt

bcrypt, from Provos and Mazières, "A Future-Adaptable Password Scheme", USENIX 1999: https://www.usenix.org/legacy/events/usenix99/provos.html

A password hash whose cost is a number you choose rather than a number the algorithm fixes: the same password and salt are run through 2^cost rekeyings of Blowfish, so raising the cost doubles the work for everyone, attacker included, and old hashes stay verifiable because the cost travels with them.

The text format is the one crypt(3) settled on:

$2b$12$<22 characters of salt><31 characters of hash>

bcrypt has two quirks worth knowing. It stops at 72 bytes of password, and it appends a NUL terminator, so a password and the same password with a trailing zero are the same password. Both are reproduced here rather than fixed, because a hash that does not match everyone else's is not a password hash.

concat

moonbitstack/mooncrypt/kdf/concat

The concatenation KDF of NIST SP 800-56A §5.8.1, also known as Concat KDF.

One digest per block, with a four-byte big-endian counter in front of the counters and the protocol's own OtherInfo behind it:

K(i) = H(counter(i) || Z || OtherInfo)

The counter leads. SEC1 §3.6.1 puts Z first instead and is a different function; a protocol that names one of them and gets the other produces a key that never matches, and nothing about the output says which happened.

`z` is the secret the key exchange agreed on; `other_info` is everything the protocol wants bound into the derivation — the algorithm identifiers, the two parties' key info, the length of the key being made. SP 800-56A §5.8.1 spells that structure out as a DER `OtherInfo` and calls it optional; the octets are taken as given here, because a protocol that defines its own layout (TLS 1.3, CMS, S/MIME each do) has to pass its own.

The counter starts at one, and a call longer than one digest concatenates as many blocks as it needs, each counted from one upwards.

Modes of operation for a block cipher, NIST SP 800-38A: https://doi.org/10.6028/NIST.SP.800-38A

siv

moonbitstack/mooncrypt/aead/siv

SIV, RFC 5297: https://www.rfc-editor.org/rfc/rfc5297

SIV is the one widely deployed mode that does *not* fail catastrophically when a nonce is repeated. Instead of an independent random value, the nonce is just the last component of a vector of associated data, and that vector is hashed with CMAC to produce the synthetic IV. Repeating a nonce therefore reveals only that the same message was sent twice, not the XOR of two plaintexts, which is what a repeated nonce costs in CTR, GCM and CCM.

The price is that the whole plaintext is read twice: once for the CMAC that produces the IV, and once for the CTR pass. SIV is for small, high-value messages — key wrapping, database fields, headers — not for bulk data.

The key is split in half and each half drives a different cipher: one for the CMAC, one for the CTR. Both are passed in, so nothing here assumes AES.

The scheme signs with a key whose public point has an even y coordinate, and verifies by lifting the 32-byte x coordinate back to that same point. Three tagged hashes in one signature, each with its own tag so that a value hashed for one purpose can never be reinterpreted as another:

aux the optional randomness mixed into the nonce nonce r = H(aux-mixed secret || P || m) challenge e = H(R || P || m)

The nonce is derived rather than random. BIP 340 takes 32 bytes of auxiliary randomness so that a compromised entropy source cannot leak the key, while the derivation still makes a signature reproducible when that input is fixed.

10 Key agreement

Two parties arriving at one secret

01

dh

moonbitstack/mooncrypt/kex/dh

Finite-field Diffie-Hellman over the ffdhe groups of RFC 7919.

The alternative to an elliptic-curve exchange, and the one that still buys something where a curve is not available. Every group here is a safe prime of the form the RFC searched for: p = 2^n - 2^(n-64) + { ... } - 1, generator 2, with the top and bottom 64 bits all ones. Because the subgroup order is the prime (p-1)/2, a peer's value that is not in [2, p-2] is either a unit or a member of a small subgroup, and both are refused rather than exponentiated.

The primes are RFC 7919 constants, and the script that wrote them checked each one for bit length, generator, the all-ones ends, primality and being 7 mod 8 before it emitted a digit.

The two standards are one algorithm with a different counter: HOTP counts events, TOTP counts thirty-second steps since the Unix epoch, and both HMAC that counter and read four bytes out of the digest.
